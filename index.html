What to point out

Status Pulse features

Vocabulary and architecture for the live demo — statuses, incident lifecycle, roles, and the four processes.

Service statuses

Operational Degraded Outage Unknown
  • Operational — healthy against check rules (success + recovery threshold).
  • Degraded — up but not fully healthy (e.g. slow / soft failures).
  • Outage — consecutive failures reached fail threshold.
  • Unknown — no fresh results yet, or stale / never checked.

Incident lifecycle

Investigating→ Identified→ Monitoring→ Resolved
  • Opens automatically when status becomes Outage (one active incident per service).
  • Updates may be a note or move only to the next status (no going backwards).
  • Acknowledge records that a responder saw the alert — does not resolve the incident.

Checks & thresholds

  • Intervals — fixed set (30s … 1h), not arbitrary seconds.
  • Method — GET / HEAD / POST · expected status codes.
  • failThreshold — failures in a row → Outage.
  • recoveryThreshold — successes in a row → Operational again.
  • Override — temporary manual status with expiry (owner).

Roles & visibility

Owner Responder Viewer Admin
  • Owner — services, members, plan, overrides.
  • Responder — incidents, alerts, acknowledge.
  • Viewer — read-only in the project.
  • Platform admin — jobs, outbox, audit, grant admin (not project Owner).
  • isPublic — only public services appear on the public status page.

Processes (one database)

API+ Scheduler+ Worker+ Dispatcher
  • API — JSON under /api/v1 · StatusGrep UI.
  • Scheduler — enqueues checks on interval; stale → Unknown.
  • Worker — runs HTTP check, records result, recalculates status, opens incident.
  • Dispatcher — drains outbox (mail) with retries.

Plans, mail, reliability

  • Free / Pro — limits on services & members; Pro via Paystack checkout + verify.
  • Outbox — alerts, invites, welcome, plan confirmation, public subscribers.
  • Exactly-once style — DB constraints for jobs, active incident, alert dedupe, payment keys.
  • Audit — membership, plan, acknowledge, config changes.

Live demo path (point these out)

  • 01–03 — healthy service Operational → force fail → Outage + one incident + alert → Acknowledge → recover → Operational.
  • 06 — private service absent from public status; public service visible.
  • 04–05–07 — say: retries don’t duplicate; outbox retries mail; Paystack verify before plan change.
  • UI — StatusGrep project view, service results, incidents, alerts; optional public page tab.

Acceptance scenarios

Seven behaviours the system must prove — from the first successful check to reliable billing.

07 scenarios
01 / 07Monitoring

Healthy endpoint → Operational

Register a reachable HTTP endpoint. Scheduled checks record results with success. The service status becomes Operational and that state is visible on the service and project views (and on the public page if the service is public).

02 / 07Incident detection

Failure threshold → one Outage + one alert

When consecutive failures reach the configured fail threshold, the service enters Outage. Exactly one incident is opened and one alert is raised for that continuous outage—not a new incident on every failed check.

03 / 07Recovery

Recovery rule → Operational again

After an outage, the service does not flip green on a single success. It requires the configured recovery threshold of consecutive successful checks before returning to Operational.

04 / 07Reliability

Retries without duplicates

Scheduler/worker retries (leases, re-claims) must not create duplicate check results or duplicate alerts for the same state. Uniqueness is enforced in the database, not only in application memory.

05 / 07Notifications

Failed mail recorded and retried

If alert delivery fails, the outbox records the failure and retries with backoff. The message is not marked delivered until send succeeds. Acknowledgement of an alert is independent of delivery success.

06 / 07Access control

Private service stays private

A service with isPublic = false does not appear on the public status JSON/page. Project members still see it inside the authenticated UI.

07 / 07Billing

Plan payment: fail keeps limits; success once

A failed or abandoned Paystack payment leaves the project on its current plan and limits. A successful checkout is verified before upgrade; the same idempotency path does not apply the plan twice as two independent upgrades.
